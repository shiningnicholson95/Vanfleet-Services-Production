## 1. Related Services sidebar overcrowding — fixed

**Bug:** Service page sidebars showed ~27 location+service combo links (e.g. "Sump Pump West Chester PA") instead of the ~6 real top-level services.

**Root cause:** A raw SQL query matched any page template containing the substring `template-service-`, which also matched per-city combo wrapper templates like `template-service-electrician-west-chester-pa.php`.

**Fix:** Replaced the SQL query in `template-service.php`, `template-service-longform.php`, and `page-template-service.php` with rendering from the existing `$related` array (siblings-under-parent or top-level-hub fallback, capped at 6). `template-location.php` was fixed separately using `vanfleet_services('hub')` directly, since location pages have no single "current service."

Committed as `fc0dd7a`. Deployed and confirmed live (link count dropped from ~27 to 4–6 on live pages).

## 2. Plumbing hub/detail FAQ bugs — fixed

**Bug A:** Plumbing hub pages (e.g. `/plumbing/chester-springs-pa/`) showed **electrical** FAQ content under a "Plumbing Questions" heading.
**Root cause:** `template-location-service-hub-plumbing.php` called `vanfleet_location_service_faqs('hub', $city_name)` — the same `'hub'` key the electrical hub template used, so both hub types shared electrical-only FAQ data.
**Fix:** Changed the plumbing hub template to request a new `'plumbing-hub'` key.

**Bug B:** 13 plumbing detail pages (city + service combos: water-softener, well-pumps, sump-pumps, water-heaters, tankless-water-heaters, plumber, water-heater-installation, across Chester Springs, Coatesville, West Chester) rendered a FAQ heading with a **completely empty accordion** underneath.
**Root cause:** `inc/data-location-service-faqs.php` had no entries at all for those 7 plumbing service slugs (`vanfleet_location_service_faqs()` used `??` null-coalesce, which silently returns nothing rather than erroring).
**Fix:** Added 8 new keys (`plumbing-hub` + the 7 service slugs) with 5 genuine, non-duplicated Q&A pairs each, matching the existing electrical-key style exactly, city-templated via `{city}`.

Both fixes syntax-verified in the Novamira sandbox before touching the live file (this file loads site-wide). Committed as `f21969e`. Deployed and verified server-side via direct function calls (bypassing HTTP cache) and confirmed the electrical `'hub'` key was untouched.

## 5. Chester Springs "missing -pa" wrong-redirect fix

**Bug:** Two Redirection-plugin rows used the pre-"-pa" slug `chester-springs` and pointed to wrong, generic destinations instead of the real, now-existing city-specific pages:
- id 136: `/plumbing/chester-springs/water-heaters/` → was `/locations/chester-springs/` (generic)
- id 173: `/plumbing/chester-springs/well-pumps/` → was `/plumbing/well-pumps/` (generic fallback)

Confirmed via theme-code grep and a full WP database search (`post_content`, `postmeta`, `options`) that the malformed link exists nowhere in the site's own content — external stale link (bookmark/search cache/WeChat preview cache). Confirmed via broader SQL search these were the **only 2** redirects site-wide using this missing-"-pa" pattern (checked and ruled out as systemic); 3 sibling well-pump redirects for other cities correctly point to the generic fallback because those cities genuinely have no city-specific well-pumps page.

**Fix mechanics:** `Red_Item->update()` takes the same full-details signature as `create()` — a partial `['action_data' => ...]` patch silently no-ops. Diagnosed via `ReflectionMethod`, then re-ran `update()` with the complete details array (url, match_type, action_type, action_code, action_data, group_id read from the existing item).

- id 136 → `/plumbing/chester-springs-pa/water-heaters/`: fixed, verified live same day.
- id 173 → `/plumbing/chester-springs-pa/well-pumps/`: fixed in DB immediately, but live response kept serving the old destination due to `x-kinsta-cache: HIT` on the cached 301. **Confirmed today (09-03) it has since self-corrected** — `x-kinsta-cache: MISS`, `Location: /plumbing/chester-springs-pa/well-pumps/`.

## 7. Systemic bug found and fixed: 13 pages with empty body content

User reported "no content" on the just-built Phoenixville page. Investigation of `template-service-longform.php` showed the long-form body sections (the `<h2>` prose blocks between the feature checklist and the reviews section) are rendered from **`get_the_content()` — the WordPress Page's `post_content`** — not from anything in `inc/data-services.php`.

**Root cause:** the page-creation step used earlier in this session (`wp_insert_post()`) never set `post_content` — only title, slug, and the `_wp_page_template` meta. Checking confirmed this affected **all 13** pages built via that method in sections 4 and 6 (content_len = 0 for all of them), while an earlier, separate batch of "legacy location landing pages" (built in an even earlier session, e.g. `plumbing-services-west-chester-pa`) correctly had `post_content` set and were unaffected.

**Fix, per page:**
- For 6 of the 12 section-4 pages, the staging slug **actually existed** (verified via direct `curl` status, not just WebFetch) — pulled and adapted their real staging content: `emergency-plumber-chester-springs-pa`, `water-softener-installation-service-pottstown-pa`, `water-softener-phoenixville-pa`, `hydro-jetting-services-downingtown-pa`, `drain-snaking-services-downingtown-pa`, `clogged-drain-service-downingtown-pa`.
- For the other 6, checking the constructed staging URL returned a **301 to the staging homepage** for all of them — confirmed (by fetching the staging homepage directly) that WebFetch's earlier "content" for these was actually just the homepage, not a real per-slug page. No staging source ever existed for: `plumber-malvern`, `malvern-pa-electrical-services`, `exton-pa-expert-plumbing-services`, `thorndale-pa-electrical-services`, `thorndale-pa-plumbing-services`, `water-heater-repair-and-installation-in-king-of-prussia-pa`. Wrote original body content for these instead, grounded in each page's existing `description`/`features` data, matching the established section structure and tone.
- `plumber-phoenixville-pa` (section 6) — fixed first, using its real staging content already fetched.

All 13 updated via `wp_update_post()` and confirmed live (200, `vf-page-content` blocks present, no fatal errors) via direct curl checks.

## Precautions taken systematically

- Sandbox syntax-check (`inc/data-services.php` loads site-wide) before every hand-edit, using `include` + `count()`/slug checks, then deleting the sandbox test file.
- Direct `curl` verification (headers, status code, and body content) after every deploy and every content/redirect change — bypassing tool-level and edge caching assumptions.
- Homepage + a known-good existing page checked for 200 after every deploy touching shared theme code.
- Exact-match (not substring `LIKE`) SQL checks before concluding a redirect conflict does or doesn't exist, after being burned once by a substring false positive.
- Verified staging "content" was real by checking HTTP status directly, not trusting a fetched page body at face value.
